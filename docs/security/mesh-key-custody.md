# LoopSkill mesh signing key — custody playbook

**mesh_0408 T0-D.** Normative source: `projects/loopskill/plans/2026-08-04-mesh0408-T0C-credential-trust-spec.md` §0.3.
This document operationalises that spec section; if the two ever disagree, the spec is authoritative.

## What this key is

A single Ed25519 private key that signs every mesh credential LoopSkill
issues (mesh-exec / mesh-directory / mesh-admin). It is **completely
separate** from the session-JWT HMAC secret (`JWT_SECRET` / `JWT_KEYS`) —
see `app/mesh/keys.py`'s module docstring for why the two must never merge.

## Generation

```
python scripts/mesh_keygen.py \
    --kid mesh-2026-08 \
    --private-out /etc/loopskill/mesh-signing/mesh-2026-08.pem \
    --jwks-dir /etc/loopskill/mesh-jwks
```

Rules (spec §0.3, normative):

1. Generate **on the host that will sign**. Never on a laptop, never
   transported, never pasted into chat, never committed. The keygen script
   refuses to write into a path that looks like a git working tree unless
   you pass `--force` (and `--force` is for test fixtures only).
2. Storage: a PEM file, mode `0600`, owned by the service user, **outside
   the repo tree** and outside any web-servable directory. **Not an env
   var** — env vars leak into `/proc`, crash dumps, subprocess
   environments, and `docker inspect`.
3. Access: `app/mesh/keys.py::load_signing_key()` reads it once at process
   start and holds it in memory. **No endpoint, log line, admin tool, or
   debug route may return it.** `load_signing_key()` is the only function
   in the codebase permitted to open `MESH_SIGNING_KEY_PATH`.
4. Set on the signing host:
   ```
   WR_MESH_SIGNING_KEY_PATH=/etc/loopskill/mesh-signing/mesh-2026-08.pem
   WR_MESH_SIGNING_KID=mesh-2026-08
   WR_MESH_JWKS_DIR=/etc/loopskill/mesh-jwks
   ```

## Backup

One encrypted copy in the existing Bitwarden vault, tagged
**`loopskill-mesh-signing-key`**. Loss of the key without a backup means
every credential in the mesh must be re-issued (new key, new kid, every
verifier's snapshot has to pick it up before anything works again).

## Rotation — routine (every 180 days, or on suspicion)

1. Generate a new key with a new `--kid` (do NOT overwrite the old file).
2. Publish **both** the old and new `.pub.pem` in `MESH_JWKS_DIR`
   simultaneously — the JWKS endpoint must serve both kids during the
   overlap window.
3. Wait **≥ 2 × cache TTL** (2 × 3600s = 7200s) so every verifier's JWKS
   snapshot has picked up the new key.
4. Switch signing: update `WR_MESH_SIGNING_KEY_PATH` / `WR_MESH_SIGNING_KID`
   to the new key and restart the signing process.
5. Wait **≥ max(class TTL) + leeway** (3600 + 60 = 3660s) so every credential
   signed with the old key has expired.
6. Retire the old key: remove its `.pub.pem` from `MESH_JWKS_DIR`.

**Total overlap window, spec §4.3: `2 × 3600 + 3600 + 60 = 10860s = 3h 01m`.
Round UP to 4h in any operator-facing schedule.**

## Compromise — named owner: **Adam**

**Compromise overrides availability.** Do not wait for the rotation
overlap window above — that window exists to avoid breaking in-flight
credentials during routine rotation, and a compromise is not routine.

1. **Retire the compromised kid's `.pub.pem` from `MESH_JWKS_DIR`
   immediately.** Accept that a verifier partitioned from LoopSkill (unable
   to refresh its JWKS snapshot) may continue accepting credentials signed
   with the compromised key until it reconnects or hits its own 86400s hard
   expiry (spec §4.3b). This is a real, documented gap — the mitigation is
   short TTLs (max 3600s) and this custody doc making compromise unlikely,
   not a claim that the gap does not exist.
2. Generate a replacement key immediately (`scripts/mesh_keygen.py`, new
   `--kid`).
3. Publish the new key's `.pub.pem`.
4. Switch signing to the new key.
5. Re-issue credentials to anything that needs continuous mesh access —
   there is no bulk re-issuance endpoint; each member re-mints via
   `POST /api/mesh/credentials` on its own key, which was not compromised
   (it is a distinct DB-stored API key, unrelated to the Ed25519 signing
   key).

## Honest retirement bound (do not claim "immediate")

`kid` retirement (removing a `.pub.pem` from `MESH_JWKS_DIR`) takes effect:

- Within **one cache TTL (3600s)** for a healthy verifier that can reach
  LoopSkill's JWKS endpoint.
- Up to **86400s (24h)** for a verifier that is partitioned from LoopSkill
  and is serving its last-known-good snapshot per spec §3's stale-snapshot
  grace window.

v1 of this spec called retirement "immediate, everywhere." That was false
under the spec's own caching model and is corrected here — see spec §4.3b.

## Per-class revocation exposure windows (spec §4.1)

| Class | TTL | Exposure after `kid` retirement or member revocation |
|---|---|---|
| `mesh-exec` | 900s | **960s** (900 + 60s leeway) |
| `mesh-directory` | 3600s | **3660s** (3600 + 60s leeway) |
| `mesh-admin` | 600s | **660s** (600 + 60s leeway) |

These are the TTL-bound exposure windows — a credential is never valid
past `exp + leeway` regardless of what the denylist or JWKS refresh cycle
does. See spec §4.1/§4.2 for the denylist's own (weaker, longer)
propagation bound, which does **not** protect `mesh-exec` at all (its
960s window is shorter than the denylist's 3600s propagation cycle).
